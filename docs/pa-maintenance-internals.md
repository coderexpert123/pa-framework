# pa — maintenance runner internals (extracted from pa/CLAUDE.md 2026-09-15)

- **Maintenance runner in-flight guard is per-process; skip:in-flight is reachable on the pa host since the maintenance lane can abandon a pass (AI-196 closed-by-proof, 2026-09-03; corrected 2026-09-11 — C9):** `pa maintenance run <job>` takes NO lock and runs one forced pass in its own process, so the per-process `IN_FLIGHT` set is otherwise empty at that decision point. The loop's `maintenance` lane (`runMaintenanceTick`) can abandon a pass that outruns `PA_CATCHUP_BUDGET_MS` — it logs, notifies, releases its lock and returns without waiting for `runDueJobs` — so a later tick's pass can start in the SAME process while the abandoned one is still running and `IN_FLIGHT` is non-empty. `skip:in-flight` is the intended guard for exactly that case. Do NOT add a bounded wait-and-redecide in runner.ts — the abandoned pass may never finish promptly, so skipping and letting a later tick retry once `IN_FLIGHT` clears is the correct outcome. Cross-process residual CLOSED 2026-09-04 (AI-200): `pa maintenance run` takes catchup's own pass lock around the forced run and refuses loudly (exit 1, stderr naming the holder) when it is held; `--dry-run` takes no lock (previewJob is read-only). Gotcha: the pass lock is TWO keys, `catchup` + `catchup:maintenance`, never a per-job scheme and never `catchup:topic:*` — a topic lane holds its own key while a skill runs and must not refuse a manual run. The pass-driving tick is the loop's `maintenance` lane (live since 2026-09-10) or a topic-less one-shot `pa catchup`; `catchup --topic default` (the old `run-catchup-hidden.vbs` spelling) never drives the pass and is retired. **Parallel job completions (S8, 2026-09-11) make ledger writer/reader collisions likelier:** `state.ts`'s `readLedger()` is an unlocked `readFile`, and on Windows a rename onto a file a reader holds open fails with EPERM — `renameWithRetry` absorbs it (5 attempts, backoff), but a tight poller (a 10 ms test loop reproduced it twice) exhausts the retries and the outcome write is lost. Never poll the ledger tighter than the runner's own 60 s cadence; a future watcher reads a copy or takes the lock.
- **Orphan-edit-watch (AI-214, 2026-09-08)**: daily disposition ladder (`jobs/orphan-edit-watch.ts`, logic in `lib/orphan-watch.ts` + `lib/orphan-attribution.ts`, store `~/.pa/orphan-watch.json`): paths dirty ≥6 h with no active reservation are attributed (reservation overlap → silent defer; newest Claude-transcript hit, alive iff that transcript file's mtime moved within 15 min; else unattributed); live owners defer silently, dead/unattributed families get a completion-agent topic task dispatched (finish unambiguous-and-small edits or land verbatim by pathspec commit), and only ~48 h unresolved does the operator alert fire (`ow:` buttons; `pa orphan list|land|keep|diff` is the manual surface). The job claims dispatched paths with a 4 h TTL reservation (`session: orphan-edit-watch`) so the agent's own edits don't fire `Unreserved worker edits` alerts and daily-recon skips them. `pa brain-sweep --skill-held-lock` is MANDATORY from the update-brain skill — the skill holds the git-workflow lock its child sweep would otherwise refuse on; a standalone sweep without the flag refuses commits while another process holds it. Surface-only: the job never commits; the agent and the operator button do.
- **`hasTreeChurnLock` self-lock bug, fixed 2026-09-08**: any pa-host job that guards itself against tree churn via `hasTreeChurnLock` (`lib/orphan-watch.ts`) is invoked IN-PROCESS from `runDueJobs` inside `pa catchup`'s own `catchup`/`catchup:topic:<t>` lock region — an unqualified `catchup`/`catchup:*` row match therefore always matched the caller's OWN lock and self-skipped forever (empirical: `daily-recon` ledger showed `lastOutcome:"skipped"` for its full 6-day life, zero real runs). Fixed by adding a `selfPid` parameter (default `process.pid`) that `hasTreeChurnLock` ignores a `catchup`/`catchup:*` row for when `row.pid === selfPid`; git-workflow/git-public-workflow/@build rows are unaffected (always genuinely foreign on this path). `daily-recon.ts`'s inline `hasGuardLock` (verbatim in shape, per its own comment) now calls the shared fixed function instead of carrying a second copy. **A future job on this same guard pattern must go through `hasTreeChurnLock`, never re-derive the catchup-row check inline** — that's exactly how the bug spread to a second file the first time. `lib/brain-sweep.ts:136`'s own call is unaffected by design: it runs from the standalone `pa brain-sweep` CLI process, never in-process under catchup's lock, so it never carries its own pid on a catchup row either before or after the fix.
- **brain-sweep managed set includes `BACKLOG.md` (2026-09-12, backlog-fragments wave)**: `isManagedBrainPath` is exact-match on `CLAUDE.md`/`BACKLOG.md` plus the `inventory/` and `backlog/open-` prefixes (a `BACKLOG.md` under `docs/`, `backlog/foo.md` stay unmanaged; the section files are the sole-writer net's new surface). A legacy hand-edit to BACKLOG.md is attributed or deferred `unattributed`+alerted exactly like any managed path — no new semantics; the `backlog-fragments-drain` job (the section files' sole writer) serializes on the same git-workflow lock, so sweep and drain never interleave. **`pa/scripts/verify_commit_scope.py` verifies the WHOLE `base..HEAD` range, not just HEAD**: any commit by another session landing between your recorded base SHA and yours (even the orchestrator's own plans commit, c8bd4a1 during the WP-D run) makes it exit 1 "SCOPE VIOLATION" on a perfectly scoped commit — re-run with `git rev-parse <your-commit>^` as `--base` before reporting a violation; your own commit's paths are what `git show --name-only <sha>` shows.
- **`pa catchup` wall-clock run budget (2026-09-10 incident)**: `PA_CATCHUP_BUDGET_MS` (default 15 min) bounds the WHOLE `runCatchup()` call — `catchupCommand` races it against a `setTimeout`, never against cooperative checks alone. Why a hard race and not just checkpoints: a per-skill `timeout`/`idle_timeout` already exists (run.ts's shell-skill `timeoutTimer`; workers.ts's `executeWorker`) but only bounds THAT skill's own child process, not the `pa catchup` process awaiting it — and a spawned worker child is NOT `.unref()`'d (worker-exec.ts:465, deliberately, "we still want this process tracked as a normal child for waiting/reaping"), so merely not-awaiting an abandoned dispatch does NOT let the Node process exit on its own; only `process.exit()` does. Production really calls it; tests inject a no-op via `_setExitForTest` (same pattern as `projects/telegram-bot/src/main.ts`'s `_setExitForTest` — now used twice in this repo, worth reaching for again before hand-rolling a new one). Cooperative `isBudgetExceeded()` checkpoints (mirroring the existing D2 lock-lost ones) still matter for the non-stuck-but-slow case (stop starting NEW skills without needing the hard exit). An abandoned dispatch is never killed by catchup itself — it keeps running under its own timeout, or gets reaped by `orphan-worker-reap` once catchup's PID is gone.
- **Catchup watchdog, lane progress files, bounded store queues and the stall exit (2026-09-16)**: read `docs/catchup-watchdog.md` before touching `runMaintenanceTick`, the lane timer, `lib/stall.ts` or the launcher generators. A maintenance pass past its budget is abandoned without exiting, a store stall exits with code 4, and a stale lane is killed from outside.
