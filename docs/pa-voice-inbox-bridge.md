# pa — voice-inbox bridge (extracted from pa/CLAUDE.md 2026-09-15)

- **Consuming a sibling package's compiled output when it ships no `.d.ts` (`voiceInboxFallbackJob`, AI-214 follow-up F-A, 2026-09-09):** `projects/voice-inbox`'s tsconfig has no `"declaration": true` (unlike pa's, which does — that's why the bot can statically import `pa/dist/src/lib/*.js`), and pa's own tsconfig is `strict` with no `noImplicitAny` override, so a literal static `import` of `projects/voice-inbox/dist/*.js` fails to compile (TS2307/TS7016). Fix: a **dynamic** `import()` whose specifier is a computed value, not a string literal — TS skips module resolution entirely for a non-literal `import()` argument and types the result `Promise<any>`, so an `as <LocalInterface>` cast gives type safety on the consuming side with zero new files and zero changes to the other package's build config. Needs `pathToFileURL(absPath).href` on Windows (a raw backslash path is not a valid ESM specifier). See `pa/src/lib/maintenance/jobs/voice-inbox-fallback.ts`'s `defaultLoadVoiceInboxModules` for the pattern — reuse it verbatim for any future pa↔voice-inbox (or pa↔any-undeclared-package) cross-import rather than re-deriving it. **This also creates a build-order coupling `.github/workflows/ci.yml` does not enforce**: that job's production path and its own test fixture both need `projects/voice-inbox/dist` built and current, but CI never builds or tests that package at all (verified 2026-09-09 — no `voice-inbox` hits in the workflow file), unlike the pa→bot build-step ordering the workflow already documents. Flagged as a follow-up, not fixed here (`.github/workflows/ci.yml` was outside this wave's file ownership). **The fixture itself is an unpinned hand-copy (2026-09-09):** `pa/tests/voice-inbox-fallback.test.ts`'s `FIXTURE_SCHEMA_SQL` is a hand-copy of `projects/voice-inbox/src/ledger.ts`'s `LEDGER_SCHEMA_SQL`, read-not-imported, with no automated sync check — unlike `projects/voice-inbox/tests/test_worker_scripts.py`, which reads the literal via regex at test time. A future schema bump must update this copy in the same wave (same discipline as the `buildTargetInjectionText` triple-copy in `projects/voice-inbox/CLAUDE.md`) or add a byte-sync test; nothing currently catches silent divergence — and when it bites, it bites HERE, not in voice-inbox's own suite (2026-09-13: the feedback long-press wave landed schema v7/v8 without bumping this copy, and every received-route test in `pa/tests/voice-inbox-fallback.test.ts` failed with `route_task.py` KeyError 'feedback_about' — the pa gate caught it, the owning package's tests stayed green).
- **`voiceInboxFallbackJob` now loads a THIRD dynamic-import module, `conversation-briefing.js` (AI-conversation-context WP-3, 2026-09-10)**: `defaultLoadVoiceInboxModules` returns `{ledger, bridgeWriter, briefing}` — same pattern as the two above, same file (`voice-inbox-fallback.ts`). `handleStaleRouted`/`handleDeadDispatch` each compute the briefing (render base → `briefing.briefingBudget` → `briefing.buildConversationBriefing`) inside their own try/catch nested INSIDE the outer `transitionTask` try (db still open), logging `briefing-skipped` and leaving `conversationBriefing = ''` on any failure — a briefing failure must never abort a replay that would otherwise deliver. **Gap closed same-day (E34, follow-up build after WP-3 correctly refused to reach outside its file ownership):** `RunningDispatchRow` (`pa/src/lib/voice-inbox-ledger.ts`) now selects `conversation_id` (`NOT NULL` on `tasks`, never optional) — `handleDeadDispatch` reads `task.conversation_id` directly, the same way `handleStaleRouted` reads it off `StuckTaskRow`, no defensive cast. Proven red-then-green: reverting both the SELECT/interface and the fallback's read back to the pre-fix throw-and-skip shape fails the dedicated test (`voice-inbox-fallback.test.ts`'s "threads the conversation briefing into a dead-dispatch replay (E34)"); restoring passes it. `voice-inbox-ledger.test.ts`'s `buildDispatchLedger` fixture needed the new column too — a selector's own direct test can carry a stale hand-copied fixture schema that the production SELECT no longer matches; check test-file fixtures, not just the fixture used by the *consumer's* test, whenever a shared row-selector's column list changes.
- **`voiceInboxFallbackJob` stuck-placement alert + legacy-orphan heal (2026-09-12 dispatch-reliability incident):** replay targets (stale-routed or dead-dispatch) already carrying `PA_VOICE_INBOX_FALLBACK_REROUTE_ALERT_AFTER` (default 3; 0 disables; parsed by `envCount()`, deliberately NOT `envMs()` — envMs maps 0 to the default, the inverse of "0 disables") prior `task.rerouted` events page the operator via the injectable `notifyFn` (default `notifyUser`, dedup key `voice-inbox-stuck:<task_id>`, severity warn) BEFORE re-injecting; the alert never gates the replay — the diagnosed gap was unbounded silent retries (task vi-7ab45f7bd3b7: four re-injections over 95 min, no pickup, no alert). The routed arm of `selectStuckTasks` deliberately carries no `worker_resource` filter: voice-inbox's `transitionTask` clears identity on entering `routed` (same-day fix), making routed+identity impossible-by-construction, so any match is a legacy pre-fix leftover the replay itself heals.
- **`voiceInboxFallbackJob` dead-dispatch arm decides from the OS, not the registry (t-31 fix 1, 2026-09-13)**: the worker-pids registry can silently outlive its entries (bot restarts), and that stale entry used to suppress the dead-dispatch replay forever — a `running` task whose worker had died stayed unserved because `stillRegistered` was checked as registry MEMBERSHIP. `isDispatchAliveOnMachine()` (exported from `voice-inbox-fallback.ts`, pure over injected reads) may conclude "dead" only when NO live process is found: prong 1 — the entries matching the dispatch id contribute pid + recorded `descendants` to `areProcessesAlive()` (the wrapper can die while the CLI child lives); prong 2 — `findProcessesByCommandLine()` (new process-tree export, SAME cached snapshot, never per-PID CIM) scans command lines for the dispatch id, catching the live-but-unregistered worker. Both reads are injectable (`areProcessesAliveFn`, `findProcessesByCommandLineFn` — same hook shape as bgtasks); tests that reach the running arm MUST inject both or the default spawns a real snapshot query. A registry entry alone is a hint, never the decision. Kill-before-replay + replay dedupe + thread-notify are BUILT (t-32, 2026-09-13, same file): `collectDispatchAliveTargets()` (same two prongs as `isDispatchAliveOnMachine`, which remains as its one-line boolean wrapper) returns the alive-pid SET so the alive decision and the kill collection are one implementation; a 20-min-silent OS-alive dispatch goes through `attemptKillBeforeReplay()` — kill each live pid+descendant (injectable `killProcessFn`, default `killProcessTree`), heartbeat age + pid list logged, registry entries removed ONLY after a confirmed-clean kill (kept on survivors so the next pass can re-kill — early removal would let the next pass judge the alive dispatch dead and double-dispatch around it), survivor ⇒ `kill-incomplete`, pass aborted, retried next tick. `handleDeadDispatch` re-reads the task state on the already-open write connection right before acting — terminal or vanished row logs `running-skip-terminal`, never redone (deliberately fail-CLOSED; `voiceInboxTerminalTaskIds` is fail-open and was rejected for this — it serves the bot's non-blocking lookups, and `voiceInboxTaskStates`, the state+`routed_to` reader the bot's late sweep consumes, is the same fail-open non-blocking family). Every kill+replay (severity warn) and dead replay (info) sends one thread line via `notifyFn`, topic override `{chat_id: String(chatId), thread_id}`, dedup key `voice-inbox-redispatch:<task_id>:<dispatch_id>` — never a route-queue entry (that would spawn a worker); a notify failure logs `redispatch-notify-failed` and never blocks the replay, and a kill followed by a terminal-dedupe skip sends no line. Three t-31 skip tests were REWRITTEN to the kill+replay policy (same fixtures/prongs, now asserting exact kill targets) — the prong coverage survives, the pure "alive ⇒ untouched" assertions do not, by design. The cmdline-scan prong stays inert in production on Windows (dispatch id is env-only, in no command line) — documented, not "fixed".
- **`pa auth` broker (AI-220 auth broker Phase A WP-D, 2026-09-10)**: `pa/src/lib/auth/{store,shapes,profiles,ledger-bridge}.ts` + `pa/src/commands/auth.ts`. `ledger-bridge.ts`'s `loadVoiceInboxModules` follows the D10/`voiceInboxFallbackJob` dynamic-import pattern verbatim, now importing FOUR modules (`ledger`, `bridge-writer`, `answer-resume`, `config`) instead of two — every pa-side auth test injects this loader (see `pa/tests/auth-cmd.test.ts`'s in-memory-then-file-backed better-sqlite3 fakes), never touching `projects/voice-inbox/dist`. - **Routing retry (`lib/voice-inbox-route-retry.ts`, 2026-09-16)**: `returnVoiceTaskForRouting` is the second bot-process ledger writer after the transcription drain — both write only through voice-inbox's compiled `transitionTask` via `defaultLoadVoiceInboxModules`, never hand-built SQL (the "bot never writes" line in `voice-inbox-ledger.ts`'s header predates both). It repairs a never-routed task (`received`/`running`, `routed_to` NULL) to `routed` for the settling thread's topic with the `VOICE_ROUTE_RETRY_REASON` sentinel, re-reading inside an IMMEDIATE transaction. `voiceInboxRouteRetryPendingIds` is deliberately a separate reader, not a new `voiceInboxTaskStates` field: that reader's hand-built fixtures (`voice-inbox-ledger.test.ts`, `voice-inbox-transcribe-drain.test.ts`) create `tasks` without `routing_reason`. The fallback's stale-`routed` arm redirects the retry shape into `handleDeadDispatch`'s never-routed branch (`expectedState 'routed'`), whose recheck skips on any change of state, `routed_to` or reason.
- **Shared transcription action + bot-tick drain (2026-09-16)**: `pa/src/lib/voice-inbox-transcribe.ts` holds the ONE transcription implementation, moved out of `voice-inbox-fallback.ts`, which re-exports the moved symbols so existing importers compile unchanged. `defaultLoadVoiceInboxModules` — the computed-specifier dynamic-import pattern the first bullet tells you to reuse — now lives there. `transcribeVoiceInboxTask(task, ctx, deps)` runs: claim (`voice-inbox-transcribe:<task_id>`, blackboard, try-once, fresh contextId) → live-state recheck → audio/size checks → infra bound → retry pacing (`transcribeAttemptDue`, 2/5/10 min off the newest marker) → `transcribe_voice.py` → `task_transcribe.py`. `ctx.caller` picks the log module and the `--reason` suffix (`(deterministic fallback)` vs `(deterministic transcription)`).
- `defaultRunScript` spawns python itself and, at its timeout, kills the process tree by the captured PID and resolves at once: `execFile`'s own timeout killed only the direct child, and its promise waited on `close`, which a grandchild holding the pipe could delay indefinitely. `pa/src/lib/voice-inbox-transcribe-drain.ts` is the bot-side scheduler. `kick()` is synchronous and never awaited. It runs a 5 s scan throttle and 3 concurrent attempts, gives each attempt a deadline (exec timeout + 120 s) that frees its slot even if the attempt never settles, and gates retries with an in-memory `notBefore`.
- Its notify is fire-and-forget, and nothing on its path awaits a log flush or `updateJobState` — the bot process shares pa's in-process serializers, the 2026-09-15 catchup lane wedge class. `voiceInboxRouteHoldStates` feeds the bot route drain's transcribing hold. The fallback's `selectStuckTasks` takes a separate `receivedStaleMs` (5th argument): the transcribing arm defaults to 2 min, while the received arm stays at 6 min so deterministic routing never races the LLM routing worker earlier than before.
- **Typed routing (2026-09-17)**: `lib/voice-inbox-typed-route-action.ts` is the ONE typed placement path (claim `voice-inbox-route:<id>`, then `route_task.py`'s argv); the bot drain and the fallback's received arm (last resort) both call it. Knobs: CONFIGURATION.md § TypeSafe typed routing.
