**Read this before running or gating test suites in this repo.**

## Rule 10: Test Runs Are Isolated, Serialized, and Off D:

These rules lived in global machine notes until 2026-08-23; they are repo-operational, not machine trivia.

- **One test process on this machine at a time.** Gates run in the FOREGROUND, serialized. Never launch a suite in the background and move on (2026-08-15: a background suite run alongside two other agents starved the machine to a hard hang).
- **Agent test runs belong on C:, never on D.** `git worktree add --detach <gate-root>/<name> <sha>` gives a same-repo, zero-contention checkout in seconds (objects stay in the D: `.git`); `git worktree remove` when done — but if you junctioned `node_modules` into the worktree, delete the junctions FIRST (`cmd /c rmdir <gate-root>\<name>\pa\node_modules`, same for the bot): `git worktree remove --force` follows a junction and empties the LIVE `node_modules` on D: (2026-08-23: both packages' modules were wiped for ~90 s; `npm ci` restored them). Prefer `npm ci` in the worktree (~35 s) over junctions. (2026-08-15: a pytest on D: starved the production poll tick 25 min.)
- **Verify the worktree's base before trusting any gate.** A harness-created worktree can be cut from a stale ref: `git merge-base main <branch>` must equal `main`, else the gate measures a different tree.
- **Point TEMP at a fast-drive scratch dir for every test run:** `TMP=<scratch> TEMP=<scratch> npm test -- <file>`. The user TEMP dir lives on D:, so temp sqlite files fsync against the saturated HDD (2026-08-15: a trivial test "hung" 30+ min, passed in 22 s with TEMP on C:). Both run-tests.mjs wrappers do this via `PA_TEST_TMP_DIR` (falling back to the deployment's conventional scratch dir if present).
- **Run a scoped test through the package's own `npm test`:** `npm test -- <file.test.js>` (matches on basename, still preloads the safety file, still excludes quarantined files, exits 1 if nothing matched). **Never hand-construct a `node --test` invocation** — it skips the `--import test-env-setup.js` preload, so `PA_HOME` resolves to the real `~/.pa` from the file's first line. That leak sent 3 real Telegram alerts to production on 2026-08-17.
- A slow run under contention is "unverified, I/O-starved" — never evidence either way.
- `npm test` takes `@build` itself (Rule 4), so a scoped run inside an orchestrated wave should set `PA_BUILD_LOCK=0` to avoid six builders serializing behind each other; the integrator's full-suite runs must NOT set it.
- **Test the blast radius, not the world (operator directive 2026-09-16).** Builders and verifiers run the tests of the changed files PLUS the tests of every module that imports or executes them — derive that set from importers and call sites (grep), never from the touched file names alone — and keep each package's known-bad gate. Run a full package suite only when it can see what scoped runs cannot, and only once: (a) the change sits on a path every request executes (prompt building, the send path, the drains, broadly imported shared libraries); (b) once per wave per touched package, before the wave's last live deploy — code goes live on commit + build here, long before any push. One agent owns that run (the verifier or the orchestrator), never builder and verifier both. Every "verified" claim names its scope: `scoped: <files>` or `full: <package>`.

## Rule 18: Serialization-lock hygiene

The suite lock covers SUITES only — never held across an `@build` wait (builds serialize themselves); released in a separate shell command (runners linger minutes past their summary); stale-lock removal (no live runner, verified) needs lead sanction, and `rmdir`+`mkdir` re-acquire must be ONE shell command — two tool-call round-trips is a race a queued sibling wins. Suite serialization itself is machine-profile-gated: `pa doctor`'s `suggestedSerializeSuites` (HDD true, SSD false).

**Holder identity (2026-09-13, after three stale-lock incidents each costing CIM archaeology):** the lock is taken through `node pa/scripts/testlock.mjs acquire <session-label>` and released through `node pa/scripts/testlock.mjs release <session-label>` — the helper writes a `HOLDER` file (`{session, pid, at}`) into the lock directory, so `node pa/scripts/testlock.mjs status` names the holder with zero process archaeology, and a refused release names the holder too. Staleness check = read HOLDER (`status`); kill nothing; a holder mismatch escalates to the lead. A lock directory with no HOLDER file is pre-convention: bare `release` clears it, and `acquire --remove-stale` clears-and-reclaims it as rmdir+mkdir in one invocation with the evidence printed; anything else — a holder you didn't write, an unreadable HOLDER — needs `--force` (the printed sanction note is the assertion). Tests inject `PA_TESTLOCK_DIR` and never touch the machine-global lock; `PA_TESTLOCK_POLL_MS`/`PA_TESTLOCK_WAIT_MS`/`PA_TESTLOCK_GRACE_MS` are the matching timing knobs.

**Heartbeat + resolvable staleness (AI-255, 2026-09-16):** HOLDER also carries `beat` (refreshed by the bus-inject hooks while the owning session is alive — `pid` is the short-lived acquirer process, NEVER a liveness signal) and `sessionPid` when the owning session resolves (explicit `--owner-pid`, or the session label matching a bus-registry entry's address/`nativeSessionId`). `acquire --remove-stale` now also clears a HELD lock when `beat`/`at` has aged past `PA_TESTLOCK_STALE_MS` (default 30 min — an idle holder) or when a resolved `sessionPid` is dead (the owning session is gone), printing which signal fired. On acquire timeout the holder's session, when it resolves to a live bus address, gets a best-effort `pa bus send` nudge to release or keep heartbeating — `PA_TESTLOCK_NO_NUDGE=1` or `--no-nudge` suppresses it, and a nudge failure never masks the timeout.
