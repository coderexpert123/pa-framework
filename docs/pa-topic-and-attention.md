# pa — topics, task lanes & attention (extracted from pa/CLAUDE.md 2026-09-15)

- **Topic-ownership registry** (2026-09-05, AI-194): `~/.pa/topic-ownership-registry.json` — hand-maintained JSON object keyed `"<chatId>_<threadId>"`; rows carry repo-relative `owned` path prefixes (segment-matched) and at most one row is `role: "catch-all"`. Precedence everywhere (daily-recon attribution, catch-all routing): orphan ledger (who made the change) → registry (who owns the area) → catch-all/`topics.support`. Loader `pa/src/lib/topic-ownership.ts` is fail-to-empty (missing/corrupt → empty registry + ONE warn-once per process, never throws); `loadSupportTopic` keeps its exported seam in daily-recon so the bot's consumers track pa dist alone.
- **Task-lane activity reader** (2026-09-05, AI-197): `pa/src/lib/task-lane-activity.ts` aggregates the topic-event log into per-conversation task outcomes for the analyzers — caps (`TASK_LANE_PROMPT_MAX_TASKS=12`, `TASK_LANE_PROMPT_MAX_TOPICS=6`, `TASK_LANE_MAX_TRACE_JOINS=10`) are consts, not knobs; the trace join is an injected lookup — the module never imports ref-lookup, callers wire `lookupTraceByTaskRef` (tail-most `task_ref` match wins); `formatTaskLaneReportLine` returns null on zero activity, so the nightly report line prints ONLY when tasks ran.
- **Attention channel is OPT-IN (2026-09-11, vi-08b2360d27b3)**: `lib/attention.ts`'s `toastEnabled`/`pingEnabled` (and so every `notifyAttention`/`pa ping`/`pa auth request` page) no-op unless `PA_ATTENTION_ENABLED=1`; `PA_NOTIFY_DISABLED=1` stays the absolute kill switch, `PA_TOAST_DISABLED`/`PA_PING_DISABLED` gate their single legs. The operator-facing channel is the voice-inbox web app's browser notifications — do not "fix" the inverted default back. Test discipline: any test asserting an ENABLED leg must set `PA_ATTENTION_ENABLED='1'` (all of `attention.test.ts`'s enabled-leg cases do); the gate functions are checked in order, so an enabled-looking assertion that still sees `disabled` is a missing opt-in flag, not a broken spawn.
- **Nightly topic consolidation (`pa/scripts/topic_consolidation.py`, 2026-09-14)**: memory-consolidation Step 4C — small overlapping registry topics merge into their larger active home, deterministic, no LLM. Frozen rules: K=3 turns/24h census floor, title token-containment ≥ 0.5 (stopword list kills the per-worker `*-support` false pairs — WITHOUT it `claude-support`/`zclaude-support` clear the threshold on the shared stopword and merge two deliberate domains), target must be ≥ K turns and strictly larger. Never a source: thread 0, EXEMPT.json rows (the "operator hand-created" guard rides the registry that exists), live records (running/queued orchestrator threads, open/`.running.json` topic tasks — NOT `.notes.json`, those are durable operator state), thread-id collisions, and the top-3-by-activity **among topics with turns > 0 only** — ranked over all topics, the 0-turn tail fills the top-3 on quiet days and the guard silently eats the whole feature on exactly the settle-down days it exists for (caught by my own first test draft). Write order is fail-closed: target brain append → source `folded-into` stamp → registry removal LAST → audit row; a registry write failure leaves the topic registered. Census skips valid-JSON non-object archive lines (a bare JSON string line crashed the first draft — the archive is not guaranteed object-per-line under torn writes). Tests freeze the clock by swapping the module's `tc.datetime` (run() is the only now() reader); fixtures are window-relative. Live dry-run on real data: zero merges on a quiet day is the CORRECT result — targets need ≥ K turns today.
