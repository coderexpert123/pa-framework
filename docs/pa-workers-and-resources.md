- **exec-fed sensors (c-disk-floor-watchdog, 2026-09-03):** `child_process.exec` routes through cmd.exe — a bare PowerShell expression fails (".Free was unexpected at this time"); wrap it `powershell -NoProfile -Command "..."` (the process-tree.ts:94 convention). And `Get-PSDrive` wants the drive name WITHOUT the colon: `Get-PSDrive C:` matches nothing, exits 0 with EMPTY stdout, and `Number('') === 0` turns that into a sensor reading of "0 bytes" that fires a real alert. Parse exec output strict-digits and embed the raw output in the throw — injected-execFn tests cannot see either class of bug; only the live CLI smoke crossed the seam.
- **DEFAULT_MODEL_PRICING rows are TIME-BOUND (2026-09-04):** the gemini-3.6/3.7/3.8-flash rates ($0.75/$3.75/$0.075 per 1M) are the official page's through-2026-12-31 prices and DOUBLE on 2027-01-01 — re-check `src/lib/model-pricing.ts` + the three doc/example cost tables ~2026-12-15 (backlog item tracks it; verified against ai.google.dev's page, updated 2026-09-03 UTC).
- **`classifyGeminiError` (rate-limits-gemini.ts) has a text-only rule ahead of the JSON-blob rules (fixed 2026-09-09):** agy's own CLI wrapper prints "Error: Individual quota reached... Resets in <duration>" on a terminal subscription-quota fault, carrying NO 429/RESOURCE_EXHAUSTED marker — every JSON-blob rule below it (and the `!has429` guard) is blind to this shape, so it silently fell to null for a month (`rate-limit-unparseable.jsonl` rows from 2026-08-09, reason `no-session-evidence`, zero cooldowns ever written). It now returns `classification: 'quota-exhausted'` with a NEW `source: 'gemini-cli-text'` — a source value chosen specifically so `rate-limits.ts`'s agy branch can route it to `alertAccountExhausted` (the same terminal-fault alert zclaude's Zhipu-1113 fault uses) WITHOUT also alerting on Rule 4's self-healing `quota-exhausted` (JSON blob + server `retryDelayMs`, source `gemini-stderr`) — those two rules deliberately share a classification name but not a source, and any future agy alert-routing decision must key off `source`, never `classification` alone. Default cooldown when no "Resets in" tail survives (agy's own message gets stderr-sliced to 100 chars before logging, which is why every historical specimen is tail-less) is 360 min, matching `rate-limits-claude.ts`'s `ACCOUNT_EXHAUSTED_COOLDOWN_MINUTES`. **`parseResetsInMinutes`'s per-unit regexes were unparseable against agy's own real format (fixed 2026-09-10):** each unit (`d`/`h`/`m`) required a trailing `\b`, which never matches between a unit letter and the digit starting the next unit (both are `\w`) — every real specimen sampled ("53h9m30s", "12h13m34s", no space between units) silently failed to parse and fell back to the 360-min default regardless of how much longer the real reset actually was. Fixed by replacing `\b` with `(?![a-z])` on all three units.
- **agy/agyc error-loop + no-progress guard, and the `.error` vs `.response` bug on quota-exhausted `result` events (worker-exec.ts, 2026-09-10 incident):** an agy dispatch alternating `agent_response`(empty `text_delta`)/`error_message` step_update events can run for 10+ minutes without ever emitting a `result` event, holding the worker slot and looking "alive" in the heartbeat log the whole time (`[heartbeat] agy: subprocess running` reports liveness, not progress — it never stops just because nothing is getting done). Two independent guards now kill such a run via the existing `killWithMessage`/`killWorkerTree` path: (1) `AGY_ERROR_LOOP_THRESHOLD` (2, lowered from 3 — Oracle, 2026-09-17: waiting for a 3rd occurrence just burned time budget on a worker already shown to be looping) consecutive `error_message` step_update events with no usable output (non-empty `text_delta`, or a real `result.response`) in between — resets on ANY usable output, so a single self-healing blip never fires it; the kill message names both the worker and the exact step count (`agy-error-loop after N consecutive error_message steps ... (worker: <name>)`) so a failover-exhaustion report shows each attempted worker's specific reason instead of a bare message; (2) a wall-clock companion (`PA_AGY_NO_PROGRESS_TIMEOUT_MS`, default 5 min) for the silent variant the counter can't see (a stream that keeps emitting bytes with no error_message steps at all). The heartbeat's "subprocess running" line now carries an agy progress marker (steps seen, last-usable-output age) instead of being indistinguishable between a spin and a healthy long run. Separately: a real quota-exhausted `result` event carries the phrase on **`.error`**, not `.response` (verified against production tee output — `status:"ERROR"`, `response:""`, message exclusively on `.error`); the code used to read only `.response`, so the phrase never reached `classifyGeminiError` at all and `~/.pa/rate-limit-state.json` got no agy entry despite the account being repeatedly quota-exhausted. Both the live and trailing-buffer NDJSON parse paths now prefer `.error`, falling back to `.response` for backward compat.
- **worker stdout/stderr decode via `StringDecoder('utf8')` — never per-chunk `data.toString()` (worker-exec.ts, 2026-09-15 WP-E):** a multi-byte UTF-8 char split across two OS pipe reads decoded per-chunk becomes U+FFFD; an em-dash inside a worker's `[PA_META]` JSON line then broke `JSON.parse` and the orchestrator silently DROPPED the `spawn_thread` (two live voice tasks never dispatched). Stdout and stderr each own a decoder, flushed in the child `close` handler (stdout's tail routes to `ndjsonBuffer` in stream-json mode, else plain stdout); the tee still writes raw `Buffer`s. The sibling leg of that incident was the devin wrapper's ANSI round-trip (see the Devin CLI notes in the user-level AGENTS.md).
- **Dynamic worker slots (2026-09-11)**: `workerSlotCount()` consults `lib/dynamic-slots.ts` — the effective cap floats between `PA_MAX_CONCURRENT_WORKERS` (ceiling) and `PA_SLOTS_MIN` by running AT the ceiling and shedding capacity only under measured pressure: one `powershell` sample per 60 s (`lib/pressure-sample.ts`, sync cached read plus fire-and-forget refresh, first call yields nothing so nothing is restricted) reports free physical, CPU busy and disk-queue length, and any of free-physical < `PA_SLOTS_PHYSICAL_BRAKE_MB` (400), cpu ≥ `PA_SLOTS_CPU_BRAKE_PCT` (90) or diskQ ≥ `PA_SLOTS_DISK_QUEUE_BRAKE` (8) cuts the pool by a quarter, never below `PA_SLOTS_MIN`, repeating on each consecutive pressured sample; after two clean samples it returns to just under the level that hurt and climbs a quarter per clean sample back to the ceiling. There is NO memory-headroom gate — that is deliberate, so pagefile capacity is counted by construction — and pressure is evaluated at most ONCE per distinct sample. The ceiling is `resolveCeiling()` in dynamic-slots.ts (env verbatim, else `clamp(4, cores×4, 64)`, else legacy 3 under the kill switch), and `workerSlotCount()` is its only caller. The module logs ONLY on a cut, a recovery raise, or an episode ending, so a healthy machine logs nothing; `PA_DYNAMIC_SLOTS=0` is the bit-for-bit legacy kill switch. `acquireWorkerSlot` gained an optional trailing `{ priority: 'routing' }` — a routing waiter polls every 250ms instead of the 5s cadence; the bot's voice-routed thread dispatches set `slotPriority: 'routing'`, everything else stays unset. The queue-timeout error string now reports the EFFECTIVE count. Knobs documented in docs/CONFIGURATION.md "Resource tuning env vars". A test handing `acquireWorkerSlot` a no-op `sleepFn` must assert reach-plus-bound (e.g. `worker-slot-29` attempted, none ≥ ceiling), never an exact attempt count (2026-09-11) — under load the do/while loop completes more than one full pass within a tiny `maxWaitMs`, which produced a 60-vs-30 flake. **Sampler inputs are Node-native since 2026-09-13 (`efcdd7b`)**: free physical (`os.freemem()`) and CPU busy (`os.cpus()` tick deltas; null on the first sample) are captured synchronously at the 60 s TTL tick; only the disk-queue length is still a PowerShell/CIM spawn and only it can be stale/null. Root cause: the previous single 3-field WMI query starved the WHOLE sample under exactly the WMI-backlog condition the sampler exists to detect, reading as "no evidence ⇒ not pressured" and holding the pool at the ceiling while the machine was crushed. The TTL tick stays the one gate that materializes a sample, so the governor still evaluates once per minute.
- **WMI snapshot storm, 4th variant (2026-09-12, `aa06f62`)**: `process-tree.ts`'s default `getProcessSnapshot()` path used the untimed plain exec while the 15 s timeout sat only in `execHidden`, and the cache-bypass `if (execFn)` fired for every production caller because `getDescendantPids`/`getCommandLines` default `execFn = execHidden` — so with 6+ workers the 30 s heartbeat piled up 67–127 WMI shells living 4 min each. Invariant now: default path → `execHidden`; bypass only when `execFn && execFn !== execHidden`; ONE in-flight snapshot promise (`_inFlightSnapshot`, cleared in `finally`) shared by concurrent callers; `worker-exec.ts` heartbeat `tickInFlight` guard (info log once after 3 consecutive skips). Tests: `process-tree.test.ts` proves the default path passes timeout/windowsHide via `_setRawExecForTest`; `worker-exec-bg-alert.test.ts` single-query invariant. Live gate after any change here: count bot-shaped snapshot shells (`… | ConvertTo-Json -Compress`, exclude your own probe's PID — a probe loop matches its own pattern) steady ≤2, never >6, ~1 s lifetime; the ≥4-worker storm condition is unverified since the fix (2 workers live at 00:50 IST). A 'cmdline sanitizer' red under 100 % CPU was load contention, not this code.
- **`pa doctor` machine-profile command (2026-09-13)**: read-only detection (`pa/src/commands/doctor.ts`, `pa doctor [--json|--text]`) — every probe fails soft to 'unknown'/false, never throws, <30 s total. Downstream tooling keys off `derivedProfile` (resourceClass/diskClass/suggestedSerializeSuites); thresholds are named constants there, not knobs. Two gotchas for future probes: (1) PowerShell's Storage module (Get-PhysicalDisk) enumerates in ~3 s standalone but >10 s under concurrent load — the physical-disk probe carries the ONE 12 s timeout + single retry (24 s worst case), and per-mount `ssdLikely` is MACHINE-level conservative evidence (any confirmed spindle ⇒ hdd for every mount), not a volume→platter mapping; (2) the unit tests inject ProbeResults and never probe live, so a NEW probe's real-world behavior is proven only by a live `pa doctor` smoke — the smoke is what caught (1).
- **PA browser (`lib/browser-launcher.ts` + `pa browser ensure|stop`, AI-246 v4, 2026-09-15)**: one shared headed/headless Chrome on `~/.pa/browser-profile` (the SAME profile the Playwright MCP D1 registration uses) answering CDP on `voice_inbox.cdp_port` (9222). `ensureBrowserChrome` is idempotent: port-answer → reuse (reports running `mode`); foreign Chrome holding the profile with NO debug port (orphaned `--remote-debugging-pipe` MCP Chromes are common — workers exit leaving chrome descendants) → spawn hand-off → 10 s timeout, and the error names the holder pids + `pa browser stop`; `stop` kills by `--user-data-dir` profile match, not just the pidfile (recycled-pid guard intact; `profileMarkerMatches` carries an end-of-value boundary so `browser-profile2` cannot false-match into the kill sweep). Mode mismatch relaunch is gated on the blackboard `skill-exclusive:browser-session` lock being FREE (held → `modeOverride: true`, existing mode kept) — `ensure` itself never ACQUIRES the lock: `classifyLock` evicts on heartbeat age, so a CLI that exits loses it within ~13 min anyway (the lock stays `pa run`-owned). `pa run` no longer tears down Chrome at run end — the credential profile stays warm across tasks. `browserSessionEnvOverlay(config)` emits `PLAYWRIGHT_MCP_CDP_ENDPOINT` (`http://127.0.0.1:<port>` form — Chrome's raw `ws://` rejects non-`/devtools/*` paths), `PA_BROWSER_CDP_PORT`, `VOICE_INBOX_PORT` WITHOUT launching Chrome (unlike `buildBrowserSessionEnv` which ensures it); the bot merges it additively into every worker env, Playwright MCP attaches LAZILY on first browser tool call (verified live: dead endpoint still answers initialize+tools/list), and the worker picks headed vs headless itself via `pa browser ensure` before its first browser call.
