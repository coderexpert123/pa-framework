# Voice-inbox bridge — telegram-bot

`CLAUDE.md` points here for the voice-inbox bridge, and this file is normative for it.

## `/pair`, the route-queue drain, and pin self-heal

`/pair` (allowed chats only) mints an 8-char pairing code and writes `~/.pa/voice-inbox/pairing-codes.json` (bare JSON array — copy `projects/voice-inbox/scripts/mint_pairing.mjs` verbatim, schema canonical there; the app's `exchangePairingCode` is its only consumer). It also drains `~/.pa/voice-inbox/route-queue.jsonl`: each line is injected as a synthetic turn tagged `__synthetic: 'route'` (`message_id: 0`, no anchor), then the queue is rewritten minus the consumed lines (consume-after-inject: a crash pre-rewrite re-injects on restart; accepted). The drain takes the writers' proper-lock across read→inject→rewrite (a concurrent append can never be clobbered); wiring: a one-poll-tick local closure beside the 60 s `BotMaintenanceDeps` seams plus ONE `await` before `drainInjectedUpdates()`. **Pin self-heal (2026-09-06)**: `refreshPinnedStatusCardInPlace` re-asserts `pinChatMessage` on the SAME message id after every successful in-place edit (topic pins are write-only in the Bot API); re-assert count == the fixture's successful-edit count (poll-loop: 1 on id 42; integration-extra: 2 on id 100 — derive per fixture).

## Voice transcription drain and the transcribing hold (2026-09-16)

`runPollLoop` builds `voiceTranscribeDrain = createVoiceInboxTranscribeDrain()` (pa `voice-inbox-transcribe-drain.ts`) beside `routeQueueDrain` and calls `voiceTranscribeDrain.kick()` once per iteration, synchronously and never awaited, immediately before `await routeQueueDrain()`. `kick()` never throws and starts at most 3 fire-and-forget transcription attempts; each attempt frees its slot at a hard deadline even if its promise never settles, so a hung transcription cannot stall the tick, Telegram delivery, or later voice tasks. The route drain receives `taskStatesFn: voiceInboxRouteHoldStates`: a plain route line (no `kind`) whose task is still `transcribing` is held — not injected, not consumed — and injects on the first drain after the transcript lands; a line whose task is `transcribe_failed` is consumed without injection; an unknown task or an unreadable ledger injects as before. With no `taskStatesFn` (tests, direct callers) nothing is held.

Pins: `voice-inbox-bridge.test.ts` (hold cases) and `voice-inbox-transcribe-wiring.test.ts` (kick placement, never awaited). A throwing `taskStatesFn` lookup also fails open, injecting as before. Held-entry logging is deduped per `q_id` (bounded `Set`, cap 1000) so a still-transcribing recording logs once, not once per tick.

## Typed routing gate (2026-09-17)

`runPollLoop` builds `voiceTypedRouteDrain = createVoiceInboxTypedRouteDrain()` (pa `voice-inbox-typed-route-drain.ts`) and passes `typedRouteFn: (taskId, state) => voiceTypedRouteDrain.gate(taskId, state)` to the route drain. The gate sees only an inbox entry (text starting `[Voice inbox task `) whose task is `received` or `routed`; the destination entry `route_task.py` appends (`[Voice task … routed`) never reaches it. `gate` is synchronous and never throws. With `voice_inbox_routing.enabled` off it returns `inject`, so behaviour is unchanged. When enabled, a `routed` task returns `drop`: the entry is consumed without injection because the task is already placed.

For a `received` task with TypeSafe configured, the gate starts one fire-and-forget attempt through pa's shared typed action and returns `hold` while it runs or after it placed the task. It returns `inject` (the LLM routing turn) once the attempt escalates, fails or passes its 60 s deadline, and after a 120 s hold. The hold needs `taskStatesFn`, so with `PA_VOICE_INBOX_TRANSCRIBE_DRAIN=0` nothing is held.

Pins: `voice-inbox-bridge.test.ts` (gate cases), `voice-inbox-typed-route-wiring.test.ts` (construction and wiring, never awaited) and pa `voice-inbox-typed-route-drain.test.ts`. A throwing gate injects. A held entry logs once per `q_id`.

## Cancel and steer verbs

A `kind:"cancel"` line is a verb: acted on, never injected. `handleRouteCancel` kills one resource (`stopWorkerByResource`), flips one thread (`cancelOneThread`, never `cancelRunningThreads`), purges its pending records; reaper Step -1 reads the ledger, fail-open. The kill is identity-guarded (`PA_WORKER_DISPATCH_ID`, WP-5 D12): `stopWorkerByResource` takes an optional `expectedDispatchId` and only kills a registered entry whose `dispatchId` matches; a bare topic resource with no dispatch id on the cancel entry refuses to kill outright (logged, never acted on) rather than trusting the shared `skill` string alone, while a thread resource (already one-per-dispatch) still kills by resource alone for backward compatibility.

A `kind:"steer"` line is acted on by `steerIntoWork` (`voice-inbox-steer.ts`), wired from `main.ts` because the bridge cannot import the thread lane without closing a cycle through `logic.ts`; the THREAD lane calls `orchestrator.handleSteer`; the TOPIC lane — the common one, since almost no topic has a thread store — kills the identified dispatch and re-injects origin plus steer as ONE turn, or injects alone in queue mode, and a topic session resume is what makes that real steering; `worker_dispatch_id` identifies a DISPATCH where the worker-pids `skill` identifies only a LANE, and **no kill may act on a bare topic resource without an id match** (a bare resource is reused by every message in that topic); a steer that cannot yet reach anything is FOLDED into a sibling route line that has not started, or HELD and retried each tick, and is injected only past `VOICE_INBOX_STEER_DEADLINE_MS`; D13's six `steer_outcome` values verbatim, queryable by `pa ref`.

## Ask mirroring (button parity)

Wherever the bot arms an operator-facing confirm/question for a voice-routed conversation, `voice-input-mirror.ts` also creates the matching typed widget (`confirm`/`choice`) in the voice-inbox ledger via the sanctioned `task_input.py create` contract, so the ask is answerable from either channel. Two mirror sites: the THREAD lane stamps the dispatch's vi- ids onto the spawned thread (`HandleSpawnArgs.voiceTaskIds` → `ThreadRecord.voiceTaskIds`) and the thread executor mirrors the ask on its success path; the TOPIC lane mirrors at main.ts's reply-send site and stamps the mirrored id onto `pending_action`/`pending_question` (`voice_task`). The reverse direction: a Telegram-side answer — typed yes/no or option text, a `cf:`/`q:` press, or a 👍/👎 reaction — cancels the mirrored widget via `task_input.py cancel` (`cancelMirroredAsk`) so the app badge cannot lie. Non-goals: TTL expiry (the widget outliving the 5-min Telegram ask is the durable one by design) and the task lane's `qt:` (voice routes never become topic-tasks). Best-effort at every site: a failed or timed-out mirror/cancel never blocks the reply.

Mirror errors are three-valued (2026-09-11): `awaiting_input` → suppressed (the worker asked in-app itself); `task …`-prefixed → ledger REJECTION notice ("the Voice Inbox app declined the ask" — the app was reached and refused); anything else → reach-failure notice. The `awaiting_input` check must stay FIRST — those errors also start with `task `.
